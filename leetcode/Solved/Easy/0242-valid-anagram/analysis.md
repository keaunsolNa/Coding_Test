## Code Review

**1. 시간 복잡도**  
- 현재 구현은 문자열을 각각 한 번씩 순회하고(`O(n)`), 두 개의 `HashMap`에 삽입·조회하는 작업을 수행합니다.  
- 이후 `sMap.keySet()`와 `tMap.keySet()`을 각각 순회하면서 다시 `O(k)`(k는 서로 다른 문자 종류) 만큼 검사합니다.  
- 전체 시간 복잡도는 **O(n + k)** 로, 최악의 경우 `k ≤ n` 이므로 **O(n)** 입니다.

**2. 공간 복잡도**  
- 두 개의 `HashMap`에 각각 문자열에 등장하는 각 문자와 그 빈도를 저장합니다.  
- 서로 다른 문자 종류가 `k`라면 각 맵에 `k`개의 엔트리가 들어가므로 **O(k)**, 최악의 경우 알파벳 전체(예: 유니코드)라면 **O(n)** 에 해당합니다.  

**3. 풀이 접근법**  
- 두 문자열의 문자 빈도수를 `HashMap`에 저장한 뒤, 두 맵을 비교하는 **빈도수 카운팅** 방식입니다.  
- `Map.getOrDefault`를 이용해 카운트를 증가시키는 전형적인 해시 테이블 기반 아날로그입니다.

**4. 잘된 점**  
- 길이가 다른 경우를 가장 먼저 체크해 불필요한 연산을 방지한 점이 좋습니다.  
- `getOrDefault`를 활용해 코드가 간결해졌습니다.  
- 디버깅용 `System.out.println`을 넣어 중간 결과를 확인하려는 시도는 학습 단계에서 유용합니다.

**5. 개선 사항**  
1. **불필요한 두 번째 맵 제거**  
   - 한 번의 `int[26]`(영문 소문자) 혹은 `int[128]`(ASCII) 배열을 사용하면 공간을 `O(1)` 로 줄일 수 있습니다.  
   - 혹은 하나의 `HashMap`만 사용하고, `t`를 순회하면서 카운트를 감소시켜 0이 되면 제거하는 방식으로 두 맵 비교를 하나의 루프로 합칠 수 있습니다.

2. **맵 비교 로직 간소화**  
   - 현재는 `sMap`과 `tMap`을 각각 순회하며 두 번 비교하고 있습니다.  
   - `if (!sMap.equals(tMap)) return false;` 로 한 줄로 대체하거나, 위에서 언급한 단일 맵 방식으로 `for`문 하나만 사용하면 코드가 더 깔끔해집니다.

3. **디버그 출력 제거**  
   - 실제 제출 코드에서는 `System.out.println`이 성능에 영향을 주고, 출력 제한을 초과할 수 있으니 제거해야 합니다.

4. **예외 상황 처리**  
   - `null` 입력에 대한 방어 코드를 추가하면 더 견고합니다 (`if (s == null || t == null) return false;`).

5. **시간·공간 최적화 대안**  
   - 문자열을 정렬한 뒤 `Arrays.equals(sChars, tChars)` 로 비교하면 **O(n log n)** 시간, **O(n)** 공간이지만 구현이 매우 간단합니다.  
   - 하지만 해시 테이블 방식이 **O(n)** 시간·**O(k)** 공간으로 더 효율적이므로 현재 접근법이 적절합니다.  

**요약**  
현재 코드는 올바른 로직을 가지고 있지만, 두 개의 `HashMap`과 중복된 비교 루프 때문에 불필요한 메모리와 연산이 발생합니다. 하나의 맵(또는 고정 크기 배열)만 사용하고, 맵 비교를 한 번에 수행하도록 리팩터링하면 코드가 더 간결하고 효율적이 됩니다. 또한 디버그 출력은 제거하고, `null` 체크를 추가하면 실전 제출에 적합한 품질이 됩니다.
