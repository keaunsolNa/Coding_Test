## Code Review

**1. 시간 복잡도**  
- **O(n)** (n = 문자열 길이)  
  - 문자열 길이가 같은 경우 두 문자열을 한 번씩 순회하면서 문자 빈도를 증가·감소시키고, 마지막에 26개의 카운트 배열을 한 번 더 순회합니다. 전체 연산 횟수가 입력 길이에 비례하므로 선형 시간 복잡도입니다.

**2. 공간 복잡도**  
- **O(1)** (상수 공간)  
  - 알파벳 소문자 26개에 대한 정수 배열 `int[26]`만 사용합니다. 입력 크기에 관계없이 고정된 크기의 메모리만 차지하므로 상수 공간 복잡도입니다.

**3. 풀이 접근법**  
- **카운팅 배열(빈도수) 이용**  
  - 두 문자열을 동시에 순회하면서 `count[char - 'a']`를 증가시킨 뒤, 같은 인덱스를 `t`의 문자에 대해 감소시킵니다. 최종적으로 모든 카운트가 0이면 두 문자열이 서로 애너그램임을 확인합니다.  
  - 이 방법은 해시 테이블을 쓰는 것과 동일한 원리이지만, 알파벳이 제한된 경우 배열을 이용해 더 빠르고 메모리 효율적입니다.

**4. 잘된 점**  
- **길이 차이 조기 반환**: `s.length() != t.length()`인 경우 바로 `false`를 반환해 불필요한 연산을 방지했습니다.  
- **한 번의 루프에 두 문자열 처리**: `for`문 하나로 `s`와 `t`를 동시에 처리해 코드가 간결하고 실행 속도가 빠릅니다.  
- **불필요한 객체 생성 없음**: 추가적인 컬렉션이나 문자열 복사 없이 원시 배열만 사용해 메모리 오버헤드가 최소화되었습니다.  
- **가독성**: 변수명(`count`)과 로직이 직관적이라 이해하기 쉽습니다.

**5. 개선 사항**  
- **입력 검증 강화 (선택 사항)**: 현재 코드는 영문 소문자만을 전제로 합니다. 문제 조건이 보장되지 않을 경우, 대문자나 다른 문자에 대한 처리(예: `Character.toLowerCase` 적용) 혹은 `if (c < 'a' || c > 'z')`와 같은 검증을 추가하면 안정성이 높아집니다.  
- **배열 초기화 비용 최소화**: `int[26]`은 매우 작아 큰 영향을 주지는 않지만, 여러 테스트 케이스가 연속으로 실행되는 환경이라면 `Arrays.fill(count, 0)` 대신 새 배열을 매번 생성하는 것이 더 간단합니다(현재 구현은 이미 새 배열을 매번 생성하고 있어 적절합니다).  
- **대안적 접근법**:  
  - **정렬 후 비교** (`O(n log n)` 시간, `O(1)` 혹은 `O(n)` 공간) – 문자열 길이가 짧고 구현이 간단하지만 현재 카운팅 방식보다 느립니다.  
  - **HashMap** 사용 – 알파벳 종류가 제한되지 않은 경우에 유용하지만, 여기서는 배열이 최적 선택입니다.
