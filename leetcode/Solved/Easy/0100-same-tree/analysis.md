## Code Review

**1. 시간 복잡도**  
- **O(N)** : N은 두 트리의 노드 총 개수이다. 각 노드를 한 번씩 방문하면서 값과 구조를 비교하므로 선형 시간 복잡도를 가진다.  

**2. 공간 복잡도**  
- **O(H)** : 재귀 호출에 사용되는 스택 공간은 트리의 높이 H에 비례한다. 최악의 경우(편향 트리)에는 O(N), 균형 트리이면 O(log N)이다.  

**3. 풀이 접근법**  
- **DFS(깊이 우선 탐색) 재귀** 방식으로 두 트리를 동시에 전위(pre‑order) 순회한다. 현재 노드가 모두 `null`이면 동일, 하나만 `null`이거나 값이 다르면 다르다고 판단하고, 좌·우 서브트리를 재귀적으로 비교한다.  

**4. 잘된 점**  
- **간결하고 직관적인 구현**: 기본적인 베이스 케이스와 재귀 호출을 명확히 구분해 가독성이 높다.  
- **불필요한 변수·조건 제거**: `p == null && q == null`을 먼저 처리해 이후 조건을 간단히 만든 점이 좋다.  
- **Java 표준 TreeNode 정의와 호환**: LeetCode 환경에 그대로 사용할 수 있다.  

**5. 개선 사항**  
- **재귀 깊이 제한**: 매우 큰 트리(예: 10⁵ 노드)에서는 스택 오버플로우 위험이 있다. 이를 방지하려면 **반복적 BFS/DFS**(Stack 또는 Queue 사용)로 구현하거나, Tail‑recursion 최적화가 가능한 언어로 변환하는 것이 좋다.  
- **조기 종료 최적화**: 현재 구현은 이미 조기 종료를 수행하지만, `p.val != q.val` 체크를 `p == null || q == null` 뒤에 두어 불필요한 값 비교를 방지할 수 있다(이미 `null`인 경우는 값 접근이 불가능하므로).  
- **테스트 커버리지**: `null` 트리만 있는 경우, 한쪽만 `null`인 경우, 값이 동일하지만 구조가 다른 경우 등 다양한 edge case를 포함한 단위 테스트를 추가하면 코드 신뢰성을 높일 수 있다.  

전반적으로 코드가 매우 깔끔하고 문제 요구사항을 정확히 만족하고 있다. 필요에 따라 재귀 깊이 문제만 보완하면 실무에서도 충분히 사용 가능한 수준이다.
