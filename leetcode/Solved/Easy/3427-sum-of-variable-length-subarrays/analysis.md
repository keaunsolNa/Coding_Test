## Code Review

**코드 리뷰**

| 항목 | 내용 |
|------|------|
| **시간 복잡도** | `O(n)` <br>루프가 `nums.length‑1` 번 수행되며 각 반복에서 상수 시간 연산만 수행됩니다. 따라서 입력 크기 *n*에 대해 선형 시간입니다. |
| **공간 복잡도** | `O(1)` <br>추가적인 배열이나 컬렉션을 사용하지 않고 몇 개의 정수 변수만 선언하므로 입력 크기에 비례하는 메모리를 사용하지 않습니다. |
| **풀이 접근법** | 현재 구현은 **연속된 두 원소의 합을 누적**하는 방식으로, “가변 길이 부분 배열의 합”을 구하려는 의도와는 전혀 다른 로직입니다. 문제에서 요구하는 것은 **모든 연속 부분 배열의 합**을 구하거나, 특정 목표 합을 갖는 부분 배열 개수를 구하는 것이 일반적이며, 이를 위해서는 **Prefix Sum + 해시맵** 혹은 **두 포인터/슬라이딩 윈도우**와 같은 패턴이 사용됩니다. |
| **잘된 점** | - 시간·공간 복잡도가 모두 최적 수준(`O(n)`, `O(1)`)이라는 점은 긍정적입니다.<br>- 코드가 간결하고 불필요한 변수 선언이 없어 가독성이 좋습니다. |
| **개선 사항** | 1. **문제 요구사항에 맞는 알고리즘 구현** <br>   - 예시: “모든 연속 부분 배열의 합을 구한다”면 `int total = 0; for (int i = 0; i < n; i++) { int cur = 0; for (int j = i; j < n; j++) { cur += nums[j]; total += cur; } }` 와 같이 이중 루프를 사용하거나, **Prefix Sum**을 미리 계산해 `O(n²)` → `O(n)` 로 최적화할 수 있습니다. <br>   - “목표 합 `k`를 갖는 부분 배열 개수”라면 `HashMap<Integer, Integer>`에 누적 합 빈도를 저장하면서 한 번의 순회로 해결합니다. |
2. **현재 로직 오류** <br>   - `sum`을 `nums[0]` 로 초기화하고 `for (i = 0; i < n‑1; i++) sum += (nums[i] + nums[i+1]);` 로 계산하면 실제로 `nums[0]` 은 두 번 더해지고, 마지막 원소는 한 번만 더해집니다. 결과가 **전체 원소의 합이 아니라** “각 인덱스와 그 다음 인덱스의 합을 중복해서 더한 값”이 됩니다. 이는 문제의 정답과 전혀 일치하지 않습니다. |
3. **경계 조건 처리** <br>   - 입력 배열이 비어 있거나 길이가 1인 경우 현재 코드는 `nums[0]` 접근 시 `ArrayIndexOutOfBoundsException`을 발생시킵니다. `if (nums == null || nums.length == 0) return 0;` 와 같은 방어 코드를 추가해야 합니다. |
4. **가독성 향상** <br>   - 변수명을 `totalSum`, `n` 등으로 바꾸고, 루프 조건을 `for (int i = 0; i < n; i++)` 형태로 명확히 하면 읽기 쉬워집니다. |
5. **테스트 케이스** <br>   - `nums = [1,2,3]` 에 대해 현재 구현은 `1 + (1+2) + (2+3) = 9` 를 반환하지만, “모든 부분 배열의 합”이라면 정답은 `1 + 2 + 3 + (1+2) + (2+3) + (1+2+3) = 20` 입니다. 이런 차이를 확인할 수 있는 테스트를 추가해 오류를 조기에 발견할 수 있습니다. |
